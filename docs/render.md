# Render deployment

Render is the selected managed host. Deployment preparation lives on branch **`render`**, based on the previous hosting work; `main` and `railway` are unchanged. The [Blueprint](../render.yaml) provisions one Docker web service and PostgreSQL 18 in Frankfurt. The [Dockerfile](../Dockerfile) serves the SPA and Nitro API together. No application disk is needed: mutable data lives in PostgreSQL, and public community configuration ships in the image.

The Blueprint selects small **paid** compute plans and 5 GB of database storage. Review Render's quoted charges before applying it. These are starting sizes, not a tested capacity guarantee. Account setup, applying the Blueprint and verifying a live installation remain in [TODO #10](TODO.md#10-complete-final-deployment-and-retention-checks).

## Validate locally

```sh
docker build --tag opine:local .
bash scripts/test-deployment.sh opine:local
```

The smoke check uses a disposable PostgreSQL container and private Docker network. It applies migrations twice, seeds that isolated database, checks packaged configuration and HTTP endpoints, and removes its resources. It never uses the development database or real Discord credentials. CI runs the same check.

## Create the installation

1. Push `render` to [the GitHub repository](https://github.com/Awesomeware/opine) and confirm its `CI` workflow succeeds.
2. Connect that repository through Render's GitHub integration. Create a **Blueprint**, selecting branch `render` and the root `render.yaml`. Use the connected GitHub repository rather than a public URL-only service, which does not support automatic deploys.
3. Review the resources and supply the prompted environment variables below. Choose a stable HTTPS origin; if the generated hostname is not known yet, update `BETTER_AUTH_URL` after creation and redeploy before testing sign-in.
4. Register that origin's exact Discord callback URL. Verify the service settings and first deployment, including migration success and database readiness.

The Blueprint defines the internal database connection, generates the auth secret and configures `pnpm db:migrate` as the pre-deploy command. The image's default command starts the server. Render supplies `PORT`; the image already listens on all interfaces. See the [Blueprint reference](https://render.com/docs/blueprint-spec) and [Docker deployment guide](https://render.com/docs/docker).

| Variable                | Configuration                                                                       |
| ----------------------- | ----------------------------------------------------------------------------------- |
| `DATABASE_URL`          | Blueprint reference to `opine-db`'s internal connection string.                     |
| `BETTER_AUTH_SECRET`    | Generated by Render; retain it across deployments and recovery.                     |
| `BETTER_AUTH_URL`       | Stable HTTPS origin, e.g. `https://feedback.example.com`, without a trailing slash. |
| `DISCORD_CLIENT_ID`     | Your Discord application's client ID.                                               |
| `DISCORD_CLIENT_SECRET` | Your Discord application's client secret.                                           |

Register `https://YOUR-HOST/api/auth/callback/discord` in Discord. The same host must appear in `BETTER_AUTH_URL`; see [authentication setup](authentication.md#configure-discord). Credentials belong in Render, never in Git or Docker build arguments. Edit `config/community.json` and `config/rules.md` in Git to change this installation's public identity and rules.

The database blocks external connections (`ipAllowList: []`). The application connects over Render's private network in the same region. Do not substitute the external database URL or local Compose credentials. See [database connections](https://render.com/docs/postgresql-creating-connecting).

## CI and deployment

`autoDeployTrigger: checksPass` selects **After CI Checks Pass**. Render waits for checks on new commits; zero detected checks or a failed check prevents automatic deployment. GitHub checks marked skipped or neutral count as passing, so keep our `Verify` job unconditional. Manual deployment is a separate path: verify the selected commit's CI before deploying manually. Observe an actual successful hosted run and the deployed revision; local validation does not prove that integration. See [Render's CI integration](https://render.com/docs/deploys#integrating-with-ci).

The deployment sequence is image build, migrations, then application startup. Render's [pre-deploy command](https://render.com/docs/deploys#pre-deploy-command) runs separately with the service environment; failure stops deployment. The previous application may still serve requests while migrations run. Keep schema changes compatible with it, or arrange a maintenance window and stop writes. The category-removal migration drops category tables and the post category column. Stop the old application for this upgrade: its queries are incompatible with the new schema. It preserves posts and tag assignments but does not convert old categories to tags or reset example content.

Redeploying an earlier commit does not undo database changes; follow the [migration guide](migrations.md).

`/api/ready` checks database connectivity. Render's [health checks](https://render.com/docs/health-checks) gate new deployments and continue checking running instances, restarting unhealthy ones. Configure failure notifications and external uptime monitoring as well. Verify `/api/health`, `/api/ready`, `/rules` and public feedback through the actual HTTPS origin.

After accepting the deployment, merge into `main` and change the Blueprint's service branch to `main`. Also change the Blueprint's own tracked branch in Render and verify the first deployment from `main`. Do not leave the service tracking the experimental branch after the switch.

## Operator access and sign-in limits

After signing in, copy your internal ID from `/api/access`. Open the application's **Shell** tab in Render and run:

```sh
pnpm auth:role grant YOUR_INTERNAL_USER_ID administrator
pnpm auth:role grant YOUR_INTERNAL_USER_ID community-manager
```

These independent roles use the existing [operator commands](authentication.md). Render's [shell and SSH access](https://render.com/docs/ssh) runs inside the service, where the private database is reachable. Use the Tags UI for subsequent setup. Never seed or reset the live database as part of deployment.

The [sign-in limiter](authentication.md#sign-in-rate-limits) uses the socket address. Behind Render's proxy, visitors may share its default allowance of 10 sign-in starts per 60 seconds. Tune `AUTH_SIGN_IN_MAX` and `AUTH_SIGN_IN_WINDOW_SECONDS` for aggregate traffic and verify behavior through the deployed ingress before the pilot. This is not a verified per-person limit; do not enable arbitrary forwarded-header trust.

## Example feedback

This branch ships community configuration for **EQ: Legends**, with a link to the official game website and game-specific rules text. Deploy the updated commit to apply it; the server reads these files at startup.

After deployment, open the **opine web service → Shell** in Render and run:

```sh
pnpm db:seed
```

This explicitly adds three fictional discussions: gear-upgrade previews, class labels for multiclass abilities, and preparation for small raids. They include eight typed comments and three fictional official responses across two posts, with `reviewing`, `planned` and `new` statuses. Their game themes draw on the [official game overview](https://www.everquestlegends.com/home); they are not reports of actual bugs or promises from the game team.

Refresh `/feedback` to see them. The command uses the service's existing private database connection, applies pending migrations and preserves real accounts and contributions. Repeated runs do not duplicate examples or overwrite edits. If an older seed was already applied, its examples remain unchanged. Example accounts cannot sign in and their notifications do not go to real users. Archive unwanted example posts with your own community-manager account; do not reset the deployed database to remove examples.

Seeding remains a manual operator action, never a build, startup or pre-deploy command.

## Recovery and release checks

Paid Render Postgres provides automatic point-in-time recovery. The documented window is three days for Hobby workspaces and seven days for Pro or higher. Confirm the database's actual recovery window in Render. A recovery creates a separate database, allowing verification before changing the application's connection. See [recovery and backups](https://render.com/docs/postgresql-backups).

Keep a protected copy of secrets, public configuration and the deployed Git revision separately. Rehearse restoration into an isolated installation, including accounts, roles, contributions and locked/archived visibility. After a recovery cutover, update the Blueprint's database reference so a later sync cannot silently reconnect the old database. Keep the original until verification is complete.

The portable [backup/restore commands](deployment.md#back-up-an-installation) require PostgreSQL 18 client tools and a host with database connectivity. They are not installed in the application image. External database connections are blocked by this Blueprint; arrange deliberate operator access before attempting an external export. Monitor storage, memory, backup coverage and costs after realistic traffic.

Before the public pilot, record hosted CI/deployment success, a recovery rehearsal, real Discord sign-in/reload/sign-out and the operational error-reporting review in [TODO #10](TODO.md#10-complete-final-deployment-and-retention-checks). Local image validation does not prove these hosted checks.
